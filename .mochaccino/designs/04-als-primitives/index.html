ALS Primitives Reference

What you can build and how the pieces fit together — with AWB mental model mapping

Purpose
The ALS building blocks in compositional order — module → delamain → agent → record → hook — with the equivalent AWB concept beside each, so you can translate either way without losing meaning.
Audience
David — translating from AWB-thinking back into ALS-thinking. Nick — verifying his abstractions land cleanly on an operator who came in via AWB.
How to read
Top of the stack is the largest container; layers shrink in scope as you descend. The blue AWB box on each layer is the translation key — read it when a Nick conversation drifts into AWB vocabulary.
Takeaway
Use this when scoping a new ALS structure — stops you reaching for AWB shapes that have no direct ALS equivalent.

Level 1
System
Top-level container — one per project, declared in .als/system.ts
▾
What you can do
  • Declare a system_id that namespaces all modules
  • Register one or more modules
  • Point to the ALS compiler via authoring.ts
Key constraints
  • One system per project (.als/ directory)
  • Standalone projects: authoring.ts must use absolute compiler path
  • system_id namespaces all downstream skill and delamain IDs
AWB equivalent
The AWB project/workspace — the root container that holds all workflows
Level 2
Module
Versioned bundle of entity + Delamains + skills, declared in module.ts
▾
What you can do
  • Define the entity type the module operates on
  • Register one or more Delamains for that entity
  • Register operator-facing skills
  • Version the bundle (v1, v2) for controlled migration
Key constraints
  • One primary entity per module
  • Module path = mount directory where entity records live
  • Version is immutable — changes require a new version bundle
AWB equivalent
An AWB workflow group — a cohesive set of workflows around one data concept
Level 3
Entity
The data record — a markdown file with YAML frontmatter that Delamains operate on
▾
What you can do
  • Define typed fields: id, string, date, delamain
  • Define named document sections (INPUTS, ANALYSIS, HOOKS, etc.)
  • Store all workflow state and generated content in one file
  • Attach state machines via delamain-typed fields
Key constraints
  • Title source fields must be allow_null: false
  • delamain-typed field is the ONLY way to trigger a Delamain
  • Two delamain-typed fields = two independent parallel state machines
  • session-field values implicitly added to frontmatter at runtime
AWB equivalent
The AWB work item / job record — the thing flowing through the pipeline
Level 4
Delamain
A state machine triggered by a delamain-typed entity field — the core runtime concept
▾
What you can do
  • Define phases (logical groupings of states)
  • Define agent-owned and operator-owned states
  • Define transitions: advance, rework, exit
  • Mark states resumable for crash recovery
  • Bind agents to states (provider + agent .md path)
Key constraints
  • NO sub-Delamains — Delamains cannot call each other
  • Triggered only by a delamain-typed field on an entity
  • Two Delamains on same entity = two separate delamain-typed fields
  • provider required on every agent state
  • Resumable states must declare session-field
AWB equivalent
An AWB pipeline/workflow — but commit-driven (not CLI-triggered) and always attached to a specific entity field
Level 5
State
A single node in the Delamain — owned by agent (auto-runs) or operator (human gate)
▾
What you can do
  • Make agent-owned: auto-runs when dispatcher finds entity here
  • Make operator-owned: waits for human action via pipeline skill
  • Make terminal: workflow ends here (completed, cancelled)
  • Mark initial: starting state for new entity records
  • Mark resumable: dispatcher can recover crashed agent sessions
Key constraints
  • Agent states must declare provider
  • Agent states must declare path to agent .md file
  • Resumable states must declare session-field
  • Only one initial state per Delamain
  • Terminal states have no outgoing transitions
AWB equivalent
An AWB step/node — but split cleanly into human (operator) and machine (agent) types
Level 5
Transition
A declared edge between states — advance, rework, or exit
▾
Transition classes
  • advance — forward progress along the happy path
  • rework — send entity back to a previous state for another pass
  • exit — move to a terminal state (cancel or complete)
  • Multi-from: same class from multiple sources to one target
Key constraints
  • Must reference states within the same Delamain
  • Dispatcher commits the transition — not the operator directly
  • Agent selects outgoing transition from legal options in runtime-manifest
AWB equivalent
AWB step connections/edges — but explicitly typed (advance/rework/exit) not generic arrows
Level 6
Agent
A Claude/OpenAI invocation bound to a state — does work and chooses the next transition
▾
What you can do
  • Read and write the entity record (frontmatter + sections)
  • Call external tools and APIs (e.g. FliHub for transcript)
  • Run parallel sub-agents (e.g. 12 analysis prompts)
  • Choose from legal outgoing transitions in runtime-manifest
  • Resume from stored session ID if dispatcher crashed
Key constraints
  • Must select a valid outgoing transition — cannot create new ones
  • Output committed to git by dispatcher, then merged to integration
  • Runs in an isolated git worktree per dispatch
AWB equivalent
An AWB agent step — but with formal state-machine bindings and git-commit-driven lifecycle
Level 6
Operator
A human gate — dispatcher pauses here, waits for human action via the pipeline skill
▾
What you can do
  • Review agent-generated content in the entity record
  • Make selections, provide input, or edit sections
  • Advance to the next state (progress)
  • Rework back to a previous state (reject/refine)
  • Exit to cancelled (abort)
Key constraints
  • No path or provider declaration needed
  • Pipeline skill is the interface — not direct file editing
  • Dispatcher will NOT advance operator-owned states automatically
AWB equivalent
An AWB human-in-the-loop approval step — but with formal transition choices (advance/rework/exit)
Level 7
Skill
A Claude Code slash command — markdown instruction deployed to .claude/skills/ and invokable as /skill-id
▾
What you can do
  • Create operator-facing commands (/fli-launch-pipeline, /fli-launch-manage)
  • Surface entity records needing attention at operator gates
  • Provide CRUD for entity records (create, list, inspect, cancel)
  • Run ALS system operations (deploy, validate, bootup)
  • File issues to external systems (/als:ghost-line)
Key constraints
  • Skills are markdown files — Claude reads and follows them as instructions
  • Deployed from .als/ to .claude/skills/ via alsc deploy
  • Claude Code Desktop: requires session restart after deploy to discover
  • Skills handle operator-owned states only — dispatcher handles agents
AWB equivalent
AWB operator console / UI commands — but implemented as Claude Code slash commands
Level 7
Dispatcher
Background Bun process that watches git HEAD for agent-owned states and invokes agents automatically
▾
What you can do
  • Poll git HEAD every 30s for agent-owned state changes
  • Create isolated git worktrees per dispatch
  • Invoke agents via Claude Agent SDK
  • Auto-commit agent output and chosen transition
  • Merge worktrees back to integration checkout
  • Resume crashed agent sessions using session-field values
Key constraints
  • Requires deployed .claude/delamains/ — alsc deploy must run first
  • Requires bun install in dispatcher/ before first run
  • Dies when Claude Code session ends — re-run /als:bootup each session
  • Only reads committed git HEAD — uncommitted changes invisible
  • No skill to deploy exists yet (filed: nfrith/als#2)
AWB equivalent
The AWB execution engine — but commit-driven and file-system based rather than API/event driven
